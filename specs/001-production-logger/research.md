# Phase 0 Research: Production Logger

**Feature**: 001-production-logger
**Date**: 2026-05-22
**Status**: All NEEDS CLARIFICATION resolved

The five interactive clarifications captured in `spec.md → Clarifications`
already resolved the highest-impact ambiguities (manager auth model,
compliance posture, dead-letter resolution UX, capture latency target,
operational health signals). This research log addresses the remaining
implementation-level decisions surfaced by the plan's Technical Context.

---

## R1. Local-first storage on tablets — localStorage vs IndexedDB

**Decision**: Use **localStorage** as the source of truth for *current
shift* state (operator session, current counter, recent captures, language
toggle). Use **IndexedDB** for the **push queue** and **dead-letter
buffer**, because both can grow beyond the ~5MB localStorage budget
during a multi-day outage.

**Rationale**:
- localStorage is synchronous, simple, and instant — perfect for the
  ≤200ms p95 capture confirmation budget.
- The push queue is append-mostly and may temporarily store hundreds of
  captures during an extended outage; IndexedDB's quota (50%+ of disk
  on most browsers) is the safer ceiling.
- Splitting source-of-truth (localStorage) from durable pending writes
  (IndexedDB) keeps the hot path synchronous while the queue stays
  resilient.

**Alternatives considered**:
- *Only localStorage*: rejected — risk of exceeding the 5MB cap on
  large dead-letter accumulations.
- *Only IndexedDB*: rejected — its asynchronous API complicates the
  capture hot path and adds 30–60ms typical overhead per read, eating
  into the 200ms budget.
- *OPFS (Origin Private File System)*: rejected — Safari/iPadOS support
  uneven; tablet target prohibits.

## R2. Sync strategy — paginated pull with watermark

**Decision**: Each device runs a 30-second loop:
1. Drain the IndexedDB push queue (per-row, with dead-letter on 4xx).
2. Pull `/captures?updated_at=gte.(last_watermark - 5min)&order=updated_at.asc&limit=1000`,
   advancing the watermark on success.

**Rationale**:
- 30s cadence matches the 30s sync SLO (SC-002).
- The 5-minute overlap protects against clock skew and devices that
  reconnect after a long offline window; idempotency (composite key
  `(line_id, operator_id, client_timestamp, payload_hash)`) prevents
  double-application.
- Pagination ceiling 1000/req is well under Supabase REST defaults and
  bounds memory on a tablet.

**Alternatives considered**:
- *Supabase Realtime channels*: rejected for v1 — adds WebSocket
  failure modes on a flaky factory wifi, and 30s polling already
  meets SLO.
- *Server-sent events from a custom edge function*: rejected — extra
  service, no benefit over polling at the required cadence.

## R3. Push queue durability and dead-letter

**Decision**: Per-row push queue in IndexedDB store `push_queue`. Each
row attempts: POST `/captures`. Result handling:
- **2xx** → row deleted from queue, audit log appended client-side.
- **Network error / 5xx** → row remains; retry with exponential
  backoff (1s, 2s, 5s, 15s, 60s, capped).
- **4xx** → row moved to `dead_letter` store (and a corresponding row
  written to the server-side `dead_letter` table on next sync), so it
  no longer poisons the queue. Surface count via Salud del Sistema +
  Admin nav badge.

**Rationale**:
- Per-row queues with explicit dead-letter prevent head-of-line
  blocking — one bad capture cannot stall every following capture.
- Exponential backoff prevents thundering herds when wifi recovers.
- The 4xx vs 5xx distinction is the standard durability rule for
  outbound queues.

**Alternatives considered**:
- *Single batched POST per cycle*: rejected — a single bad row poisons
  the entire batch.
- *Server-side queue only*: rejected — defeats local-first.

## R4. Cross-device day-reset broadcast

**Decision**: `events` table with idempotency key (uuid generated by
the initiator). On day reset, the manager device inserts a
`day_reset` event. Every device, on its 30s pull, checks for new
`day_reset` events and applies them locally exactly once (idempotency
tracked in a local `applied_events` set in localStorage).

**Rationale**:
- Reuses the existing pull cycle; no extra channel.
- The idempotency set guarantees that a tablet briefly offline during
  the broadcast still applies the reset exactly once on reconnect.

**Alternatives considered**:
- *Realtime channel*: rejected — same flakiness reasoning as R2.
- *Polling per-tablet endpoint*: rejected — duplicates the events
  pattern.

## R5. KPI math — OEE / Availability / Performance / Quality

**Decision**: Standard OEE formula, computed entirely client-side from
captures + shift definitions:
- `planned_time` = shift length − scheduled breaks
- `downtime_total` = Σ downtime row minutes (excluding planned breaks)
- `run_time` = planned_time − downtime_total
- `theoretical_output` = hourly_target × (run_time hours)
- `actual_output` = Σ units produced
- `scrap_total` = Σ scrap row pieces
- `good_units` = max(actual_output − scrap_total, 0)
- **Availability** = run_time / planned_time
- **Performance** = min(actual_output / theoretical_output, 1.0)
- **Quality** = good_units / actual_output (1.0 if actual_output = 0)
- **OEE** = Availability × Performance × Quality

**Rationale**:
- Matches industry-standard OEE definition; aligns with what plant
  managers already expect from MES vendors.
- Performance is capped at 1.0 to avoid >100% OEE when operators
  overproduce briefly above target (real-world hours can exceed target
  for a single hour; the shift-level cap is what management reports).
- Computing client-side avoids server round-trips and keeps the
  Gráficas page fast.

**Alternatives considered**:
- *Server-side stored KPIs*: rejected — adds materialization
  complexity for a small data set; client compute is sub-millisecond.
- *Performance uncapped*: rejected — confuses non-experts; the cap is
  the OEE convention.

## R6. Per-manager PIN authentication (no Supabase Auth users)

**Decision**: Manager identities stored in `config.managers` as
`{display_name, pin_hash, active, created_at}`. Tablet/laptop computes
SHA-256 of the entered PIN against the stored hash. RLS does not gate
admin actions by PIN (anon role is used); the front end is the
enforcement point. Audit log entries written from admin sessions
include the resolved manager display name.

**Rationale**:
- Spec clarified: per-manager PIN, no full identity system.
- Supabase Auth would require email/password per manager and is
  overkill for a 2-line plant with ≤10 managers.
- PIN hashing prevents trivial readback from the config table.

**Alternatives considered**:
- *Plain-text PIN*: rejected — config table is anon-readable; trivial
  exfiltration.
- *Supabase Auth + magic link*: rejected — requires email per manager
  and complicates offline operation.

**Security caveat documented in `quickstart.md`**: since RLS allows
anon DELETE on the last 36h of data, a malicious client could in
theory bypass the front-end PIN check. The 36h scope is acceptable
risk for v1 (per spec compliance posture); revisit if posture
upgrades to GMP-controlled.

## R7. Shift accounting and DST

**Decision**: All shift boundaries computed in **plant-local civil
time** using the IANA zone configured in `config.plant.timezone`
(default `America/Mexico_City`). DST transitions are handled by
`Intl.DateTimeFormat` and the host's tzdata; tests cover spring-forward
and fall-back days explicitly.

**Rationale**:
- Plant managers report by civil time, not UTC.
- Using IANA zones avoids the "what counts as 03:00 on DST day"
  ambiguity by deferring to the standard library.

**Alternatives considered**:
- *Fixed UTC offset*: rejected — silently breaks twice a year.
- *Always UTC, render local*: rejected — shift bucketing math becomes
  branchy.

## R8. Build & deploy — Vite + Vercel

**Decision**: Vite for dev server, build, and module bundling.
Multi-page mode (`vite.config.js` declares one entry per HTML page).
Output deployed as Vercel static site. `chart.js` is dynamic-imported
only from `graficas.html` to keep operator and dashboard bundles
under the 200KB gz budget.

**Rationale**:
- Vite's framework-agnostic build matches the "no frameworks" rule.
- Per-page splits guarantee the operator-tablet bundle stays minimal,
  protecting the cold-boot 5s budget.

**Alternatives considered**:
- *No bundler, raw ES modules*: rejected — would ship dependencies
  un-minified and skip tree-shaking, blowing the 200KB budget.
- *Webpack*: rejected — slower dev cycle than Vite, no benefit here.
- *Parcel*: rejected — multi-page configuration is less explicit.

## R9. Testing stack

**Decision**:
- **Vitest + jsdom** for unit + integration
- **Vitest** also drives the contract suite against a locally started
  `supabase` CLI instance (the `supabase start` Docker stack)
- **Playwright** for e2e smoke on the P1 user stories only
- **axe-core** invoked from Playwright for a11y assertions
- **lighthouse-ci** for perf regression gating in CI

**Rationale**:
- Single test runner (Vitest) for unit, integration, contract reduces
  cognitive overhead.
- Playwright is the only credible browser-automation choice that
  reliably handles mobile/tablet emulation.
- axe-core in CI fulfills constitution Principle III's a11y gate
  without requiring manual passes per PR.

**Alternatives considered**:
- *Jest*: rejected — slower, and Vite ecosystem favors Vitest.
- *Cypress*: rejected — Playwright handles real tablet device emulation
  and multi-browser more cleanly.

## R10. Internationalization (Spanish default, English toggle)

**Decision**: Custom flat string table per language under
`src/modules/i18n/{es,en}.json`. A `t(key)` helper reads the active
language from localStorage; missing keys log a console warning and
fall back to Spanish. Lint rule (`no-restricted-syntax`) forbids raw
human-readable strings in JSX-less templates.

**Rationale**:
- A full i18n library (i18next, FormatJS) is overkill for two locales
  and would add ~30KB.
- A lint rule is the cheapest way to enforce constitution Principle
  III's terminology consistency.

**Alternatives considered**:
- *i18next*: rejected — bundle overhead and no plural-form complexity
  in v1.
- *Browser `Intl`-only*: rejected — needed only for date/number
  formatting; covers no string substitution.
